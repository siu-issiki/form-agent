# 一般問い合わせの選択肢と用途審査

> 個別実装時点の記録です。統合時点の状態は[信頼性改善の検証記録](reliability-improvements-2026-09.md)を参照してください。

## 将来の承認用プロフィール

`docs/examples/campaign-choices.general-outreach.example.json` を新しい取込の `--choices` に指定する。現場で不足した問い合わせ種類7行の6表記と、同意radio2行の「同意する」を明示した代替例である。これは送信可否や個人情報同意の包括的承認ではなく、送信者が新しいジョブを作る前に内容を確認するプロフィール契約である。

- `inquiryType` は10候補。従来の9候補に6個を追加せず、従来から4個を選び、6表記を加えた。従来の「ご意見・ご要望」「お問い合わせ」「一般のお問い合わせ」「一般的なお問い合わせ」「その他のご相談」はこの代替例には含まれない。対象に応じて10個以内で選定する。
- 表記は観測した選択肢の値または全ラベルと照合する。「その他」という部分一致で専用選択肢を選ばない。候補が全て不一致なら従来どおり停止する。
- `privacyConsent` の `checked` はチェックボックスの状態指示、「同意する」はradioの明示ラベルである。広告配信、第三者提供、独立した送信内容確認への同意を追加承認するものではない。モデルは元の項目の意味とpayload keyの適合を確認し、既存の入力・画像審査を通す必要がある。
- 候補リストは承認fingerprintに含まれる。終了済みmanifest、prepared payload、既存承認、既送信ジョブへ適用しない。再送しない。既定プロフィールと照合実装は変更していない。

## 管理下で調べる用途誤拒否

実例660/728/852/878から、一般メッセージ案内、個人情報の利用目的、事業紹介サイドバー、一般のその他カテゴリを再構成した4フォームを追加した。画像上の文字化け等は別の問題として切り離した。313は「当サイトに関する質問」の専用解釈が未確定なので、緩和根拠にしない。

旧本番の実測で誤拒否が再現した場合だけ用途説明の最小修正を行う。fixtureの受信ユニットテストはモデルの用途判定を検証しない。資料請求、営業禁止、実際の専用窓口は停止を維持する。

## 検証

将来プロフィールテストは、従来内容を代替例に仮配置した状態で5成功/10失敗（7行の表記、同意2行、10候補契約）を確認し、その後代替候補を設定して15成功。実際のページ選択関数を使い、未承認ラベル・広告同意ラベル・11候補の拒否も検証する。これは実サイトへの送信成功を示すものではない。

## 再現した用途誤拒否への最小修正

旧本番97898c12の `general-inquiry-broad-messages` は `PRE_SUBMIT_REVIEW_DENIED`、内部 `FORM_PURPOSE_INCOMPATIBLE`、receiver0。モデルは一般意見・メッセージ受付に続くサービス質問の例示を、サービス専用の制限と説明した。新説明では、このような明示一般受付と「など」の例示を全体として読むことだけを追加した。別の明示用途制限や営業禁止は上書きせず、専用窓口の「その他」だけでは拡張しない。

`general-inquiry-privacy-purpose` も旧本番で同じ内部用途コード・receiver0。個人情報の利用目的を問い合わせ話題の限定と読み替えていたため、個人情報の取り扱い説明それ自体は受付話題を制限しないことを追加した。別の明示用途制限は維持する。`general-inquiry-other-category` は旧本番からsent/receiver1で、ここを根拠に緩和していない。sidebarと新本番greenは測定中。新説明の文字列テストでモデルの改善を代用せず、管理下の実判定・receiverで確認する。

## 実行エージェント側の同じ誤拒否

reviewer説明だけを修正した本番1e0f4c2bの privacy-purpose で、agentがobserve直後に「利用目的が当社またはサービスに限定」と判断した。D1は observe→finish_validation(PROHIBITION_EVIDENCE_WEAK)→finish_validation(OK)、reviewRequests0、submit0、receiver0、FORM_PURPOSE_MISMATCH。旧978のreviewer denyと異なる経路であり、初回green失敗を保存した。

同じ2文脈の説明を `systemPrompt` にもそのまま追加する。handlerの禁止検出・引用検証、用途コード、許可される操作は不変。意味の広い一般許可や、用途判定のスキップは追加しない。agent側の旧redは上記本番実行、新greenは反映後の管理下で確認する。

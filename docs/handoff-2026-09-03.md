## 計測結果（管理下テストシステム 19 シナリオ）

| 構成 | 合格 | session 停止 | 作成 API 429 | CDP 切断 1011 | exceededCpu |
| --- | --- | --- | --- | --- | --- |
| 逐次（PR #48 後） | 19 / 19 | 仕組みなし | 該当なし | 0 | 1（無言失敗、後日同型を観測） |
| 直結方式・5 並列 | 15 / 19 | 仕組みなし | 該当なし | 16 | 1 |
| 明示停止・5 並列 | 15 / 19 | 18 / 18 | 15 | 0 | 0 |
| 明示停止・3 並列 | 17 / 19 | 19 / 19 | 0 | 0 | 0 |

確定した事実:

- CDP 直結（`connect.browser-use.com`）では WebSocket を閉じても managed browser は停止せず、15 分の寿命まで同時 session 数を占有する（BrowserUse 公式ドキュメントに明記）。
- session を毎回停止しても 5 並列では作成 API が `429 Too many concurrent active sessions` を返す。この account の同時 session 上限は 5 未満で、Free プランの 3 と推定する。3 並列では 429 が出ない。
- Workers では `fetch` をオブジェクトのメソッドとして呼ぶと `TypeError: Illegal invocation` になる。fake fetcher の単体テストでは再現しない。
- `cdpUrl` は `https:` 形式で、`/json/version` から `webSocketDebuggerUrl` を取得して接続する。

## 採用済みの設計判断

- BrowserUse は Free プラン前提で `max_concurrency: 3` とする。並列数を上げるのは Pay as you go（同時 10）へ変更してから再計測する。
- Cloudflare は Free プランのため `limits.cpu_ms` は設定できない。Workers Logs（Free プランの保持は 3 日）は有効。
- 送信前の独立レビューは `INPUT_MISMATCH` の deny だけ 1 回の修正を許可し、他の deny と 2 回目の deny は `uncertain` で終了する。deny 回数は D1 に永続化する。
- codex review の指摘は脅威モデルで評価し、限定的なら設計書に残存リスクとして明記して受容する（PR #48 の 4 件）。
- E2E 用トークンは `.env.e2e`（リポジトリルート、git 管理外）に置き、`bun --env-file=.env.e2e <script>` で読み込む。

## 残タスク

優先度は「実サイトへの実送信で問題になる順」とし、BrowserUse Free（3 並列）前提で並列引き上げ関連は保留にした。

| # | タスク | 現状 | 完了条件 | 主な確認箇所 |

| P0-1 | 並列時の `multi-step` で turn 6 の `click` が `CDP_COMMAND_FAILED` になる | 実装済み（PR A）。`click` / `fill` / `select` 中の CDP コマンド失敗を `BrowserElementOperationError` へ変換し、モデルへ `ELEMENT_UNAVAILABLE` と再観察の guidance を返す。診断は `ELEMENT_OPERATION_CDP_FAILED` | 3 並列で 3 回実行し、`multi-step` が click 失敗後に続行して `sent` になる | `src/browser-use-cdp-driver.ts`（`clickNonSubmit`）、`src/responses-agent-executor.ts`（catch）、`test/worker.test.ts` |
| P0-2 | 禁止フォームの submit を handler がブロックした後、モデルが `finish_prohibited` ではなく `finish_failed` を選ぶ | 実装済み（PR A）。`SubmitProhibitedError` を追加し、`SUBMIT_PROHIBITED` と `prohibitedReasonCodes` / `pageProhibited` を返す。guidance と system prompt にも追記 | 3 並列で 3 回実行し、`external-iframe-secondary` が `prohibited` で終わる | `src/restricted-browser.ts`（`validateSubmit`）、`src/responses-agent-executor.ts`（`TOOL_ERROR_GUIDANCE`） |
| P0-3 | iframe 側の禁止文言に対して handler の禁止根拠検証が通らず `uncertain` になる | 実装済み（PR A）。`validateProhibited` が「観察が最新・URL 一致・code 不在」のときだけ input revision ごとに 1 回再観察する。`Page.getFrameTree` の補完は不要と判断（下記参照） | 3 並列で 3 回実行し、`FINISH_PROHIBITION_NOT_VERIFIED` が減少する。残る場合は診断とともに記録 | `src/restricted-browser.ts`（`validateProhibited`） |
| P0-4 | `submitting` 中に Worker を強制停止しても再送されないことの検証 | 経路は Workers テストで固定済み（PR A）。再配信は ack され、状態は `submitting` のまま残り、`job.redelivery_ignored` で検出できる | 実機での強制停止は、管理下テストで `submitting` 直後に Queue を pause → Worker を再 deploy して観測する手順を運用時に実施 | `src/worker.ts`、`src/d1-job-store.ts`、`docs/operations.md` |

P0-3 の `Page.getFrameTree` 補完について: `#frameParentIds` は初期化時の `Page.getFrameTree` に加えて `Page.frameAttached` と `Page.frameNavigated` でも登録し、エントリを削除しない。`Page.enable` は `getFrameTree` より前に呼ぶため、初期化後に増えた frame は必ず event で登録される。したがって `observe` 内での補完は不要と判断し、実装していない。
